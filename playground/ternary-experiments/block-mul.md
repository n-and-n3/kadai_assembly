# ブロック乗算と carry なし乗算の追試（2026-11-17）

実装と再現用ベンチは [`block_mul.cpp`](block_mul.cpp)。32 tritを `-1=01, 0=00, +1=10` で64 bitに格納する。以下の一般乗算は **`mod 3^32`**、つまり上位にあふれたtritを捨てる演算として比較した。範囲エラーを出す言語仕様には、その検出を追加する必要がある。

## 何を比べたか

| 方法 | 内容 | 主なコスト |
| --- | --- | --- |
| 2 trit表 | 2桁×2桁の256要素表を引き、部分積をpacked加算 | 全幅なら136部分積 |
| 4 trit表 | 4桁×4桁の65536要素表を引き、packed加算 | 全幅なら36部分積 |
| 8 tritブロック | 各ブロックを小整数へ復号、掛けて16 tritへ符号化、packed加算 | 全幅なら10部分積 |
| 16 tritブロック | 同様に16桁ずつ処理 | 全幅なら3部分積 |
| 16 trit交差項合算 | `x=x0+3^16 x1`, `y=y0+3^16 y1` とし、`xy ≡ x0y0 + 3^16(x0y1+x1y0) (mod 3^32)` | 3回の64 bit整数乗算、2回の符号化、1回のpacked加算 |
| 全幅復号 | 32桁を整数にし、128 bitで乗算・`mod 3^32`、再符号化 | 全幅復号、128 bit剰余 |

16 trit交差項の和も64 bit符号付き整数へ収まる。各16 tritブロックの絶対値は `(3^16-1)/2=21,523,360` 以下であり、`2×21,523,360²` は32 tritの最大値 `926,510,094,425,920` より小さい。そのため交差項を先に合算できる。上位項 `x1y1·3^32` は法を取ると消える。

さらに、下位積 `p=x0y0` を `p=p0+3^16 c` に分け、`c` を交差項に足してから上下16 tritを別々に符号化する「整数段階の繰り上がり」も実装した。packed加算は消せるが、2回の基数 `3^16` による剰余・商の計算が重く、このCPUでは速くなかった。

8 tritの[従来のKronecker試作](mul-div-sub.md)では、`+/-` のビット面を4 bit間隔に広げ、4回の普通の整数乗算で正負別の畳み込み係数を得る。係数ごとに3進の桁上がりを計算する代わりに、係数列を `Σc_i 3^i` と評価してから既存の符号化表を引くと大幅に改善した。さらに **4係数分の `Σc_i 3^i` を65536要素の表でまとめて引く**と、桁ごとの `%3` と `/3` の連鎖を避けられる。ただし、入力の展開と4個の乗算は残る。これは[Kronecker substitution](https://flintlib.org/doc/algorithms/polynomials/kronecker.html)の小規模な応用である。

## `PCLMULQDQ` / `VPCLMULQDQ` を試した結果

Intelの[carry-less multiplicationの説明](https://www.intel.com/content/dam/develop/external/us/en/documents/clmul-wp-rev-2-02-2014-04-20.pdf)のとおり、この命令は多項式の同次数係数を **XOR** で合成する。欲しい係数は整数の和であり、例えば `(1+3)^2=1+2·3+3²=16` に対し、carry-less結果は真ん中の `2` が消えて `1+3²=10` になる。この差は後続の3進正規化だけでは復元できない。符号の正負を別々に計算しても同様で、衝突によって無効な `11` 桁が出る場合もある。したがって一般乗算を `CLMUL` 一発へ置き換えることはできない。

例外は、**各出力次数に寄与する部分積が高々1個**と静的に分かる場合。このとき4個のcarry-less乗算で `++`、`--`、`+-`、`-+` を計算し、正負を詰め直すと正しいpacked積になる。検証用には、非ゼロ位置が `x={0,2}`, `y={1,4}` で、和の位置 `{1,3,4,6}` がすべて異なる形を使用した。符号はランダムに変えた。

条件を実行時に検査する版もある。符号を無視した0/1のsupport `a,b` について、**普通の整数乗算 `a*b` と `CLMUL(a,b)` が一致する**とき、各係数の重複はない。係数 `c_i` とすると両者の差は `Σ 2⌊c_i/2⌋·2^i ≥ 0` なので、この一致条件は必要十分である。実行時の検査と、衝突時に通常方式へ戻すコストのため、一般の8 trit入力では勝てなかった。コンパイラが疎な位置関係を証明できる場合の特殊化候補とする。

## 計測結果と判断

Intel Core i7-1355U、WSL2、GCC 13.3、`-O3 -march=native`、CPU 2へ固定。1024組を反復処理し、関数呼び出しを含むns/積。表の数値は同一プロセス内3回の中央値を複数回実行した代表値で、WSL2とCPU周波数により数割揺れる。全幅の入力以外については、積が範囲内の条件で通常の復号・乗算方式とも比較した。

| 入力 | 方法 | 観測されたおおよその時間 (ns/積) | 判断 |
| --- | --- | ---: | --- |
| 8 trit乱数 | 2 / 4 / 8 tritブロック | 97–107 / 17–22 / 5–6 | 細分化ほど部分積累積が重い |
| 8 trit乱数 | 8 trit専用復号→整数乗算→16 trit符号化 | 3.3–4.0 | この範囲では最速級 |
| 8 trit乱数 | Kronecker係数を逐次carry / 重み付き評価 / 4係数表で評価 | 170–183 / 22–25 / 9–15 | 正規化は改善できたが専用復号に届かない |
| 16 trit乱数 | 4 / 8 / 16 tritブロック | 約100 / 25–36 / 8–12 | 既存の半幅復号（約7–9）に届かない |
| 32 trit全幅乱数、`mod 3^32` | 8 / 16 tritブロック | 約67–75 / 約26–27 | 大ブロックが有利 |
| 32 trit全幅乱数、`mod 3^32` | 16 trit交差項合算 | **多くは約16–21、遅い回は約27** | 現時点でこの条件の第一候補 |
| 32 trit全幅乱数、`mod 3^32` | 全幅復号→128 bit乗算・剰余→再符号化 | 約28–31 | この環境では交差項合算が速い |
| 32 trit全幅乱数、`mod 3^32` | 整数段階で16 trit繰り上がり | 約23–24 | packed加算を消しても剰余・商が重い |
| 部分積位置が衝突しない8 trit疎入力 | `CLMUL`特殊化 / 実行時検査込み | 約2.4–3.2 / 約3.4 | 特殊化なら有利な可能性 |
| 同じ疎入力 | 8 trit専用復号→乗算 | 約3.5–4.0 | `CLMUL`との比較対象 |
| 8 trit乱数 | `CLMUL`検査＋通常方式へのfallback / 通常方式 | 約5.2 / 約3.5 | 動的判定は不利 |

小さい値同士の32 trit乗算では、両方の上位16 tritがゼロなら[半幅復号](mul-div-sub.md)が依然有利。`mod 3^32` を要求しない「範囲外ならエラー」の乗算は、エラー検出のコストを測り直してから選ぶ。今回の全幅比較は剰余ありの同じ仕様にそろえたが、8/16/32 tritブロック方式にはゼロブロック省略の最適化をまだ施していない。

## 再現

```sh
g++ -std=gnu++23 -O3 -Wall -Wextra -march=native \
  playground/ternary-experiments/block_mul.cpp -o /tmp/block-mul
taskset -c 2 /tmp/block-mul bench
g++ -std=gnu++23 -O1 -g -fsanitize=address,undefined \
  -fno-omit-frame-pointer -march=native \
  playground/ternary-experiments/block_mul.cpp -o /tmp/block-mul-san
/tmp/block-mul-san
```

2/4/8/16 tritブロック、交差項合算、carry折り畳み、`CLMUL`の適用条件を、8/16/32 tritの乱数各2万組（2 trit表は各2千組）と疎入力2万組で照合した。ASan/UBSanも通過。これは性能実験コードであり、採用するISAやオーバーフロー仕様が確定したランタイム実装ではない。
