# 復号しない32 trit加算

32桁、`-1=01, 0=00, +1=10` の packed 値を直接加える。導出の出発点は Douglas W. Jones の[Binary-Coded Ternary 加算](https://homepage.divms.uiowa.edu/~jones/ternary/libtern.shtml)と[BCD補正の説明](https://homepage.divms.uiowa.edu/~jones/bcd/bcd.html)。ここでは本プロジェクトの符号化と**64 bitいっぱいの32桁**へ適用した。

## 何を計算しているか

現在の1桁は `-=01, 0=00, +=10`。補正計算中だけ `-=00, 0=01, +=10` に変える。後者は平衡値 `t∈{-1,0,1}` を通常の3進数字 `t+1∈{0,1,2}` として表したもの。変換は両方向とも同じ式である。

```cpp
constexpr uint64_t E = 0x5555555555555555ULL;
uint64_t to_bct(uint64_t x) {
    return x ^ (~(x >> 1) & E);
}
```

通常の3進数字に直した2数 `a,b` を、64 bitの2 bit桁に詰めたまま加算する。`a+E` により各桁に1を足しておく。さらに `b` を通常の**二進64 bit加算**で足した `d` を作る。ある桁へのcarry-inを `k∈{0,1}` とすると、この桁で二進加算器が処理する値は `a_i+b_i+1+k`。これは4以上のとき次の2 bit桁へcarryを出す。条件は `a_i+b_i+k≥3` と等しいので、二進のcarry系列と欲しい3進のcarry系列が一致する。

carryを出した桁では、`d` の下位2 bitはすでに正しい3進数字。carryを出さなかった桁だけ1過大なので、1を引く。Jonesの式 `~(b ^ c ^ d)` の各境界bitから「carryなし」を取り出せる。32番目（最上位）の補正だけは64 bitの外側のbitが必要になるので、`d=b+c` のunsigned overflowを `d<b` で取り出す。

```cpp
uint64_t add_unsigned_bct(uint64_t a, uint64_t b) {
    uint64_t c = a + E;
    uint64_t d = b + c;
    uint64_t no_carry_low = (~(b ^ c ^ d) & (E & ~1ULL)) >> 2;
    uint64_t no_carry_top = uint64_t(d >= b) << 62;
    return d - (no_carry_low | no_carry_top);
}
```

`c=a+E` 自体が64 bitを越える場合でも、この最上位の式は正しい。65 bit目で `c` のcarryを `c₆₄`、`b+c` の低64 bitからのcarryを `k₆₄` とすると、`d₆₄ = c₆₄ xor k₆₄`。Jonesの検出式中の `c₆₄ xor d₆₄` は `k₆₄` となり、`d>=b` はその否定を返す。

平衡値 `x` の通常3進表現は `x+B` で、`B=(3^32-1)/2`。したがって `x+y` の表現は、`add_unsigned_bct` を使って `repr(x)+repr(y)-B` を計算すればよい。`-B mod 3^32` の2 bit桁表現は `0x5555555555555556`。

```cpp
uint64_t add_balanced(uint64_t x, uint64_t y) {
    constexpr uint64_t NEG_BIAS = 0x5555555555555556ULL;
    uint64_t a = to_bct(x), b = to_bct(y);
    return to_bct(add_unsigned_bct(add_unsigned_bct(a, b), NEG_BIAS));
}
```

実装は[`packed32.cpp`](packed32.cpp)の `trit_add_bct_fast`。逐次桁加算、変換して整数加算する版と同じ結果になることを、20万組の全幅乱数、上位4桁・下位4桁それぞれ全81×81組、境界値で照合した。範囲外の和については **`3^32` を法とする循環**まで照合した。この循環を言語仕様として採用するか、範囲エラーにするかは別途決める。範囲エラーを選ぶ場合、別途あふれ検出が必要。

## 速度と限界

同じi7-1355U、`-O3 -march=native`、WSL2、`taskset -c 2`で5回実行した中央値は、元の符号化のまま加算する本方式が **3.92 ns/値**、復号→CPU加算→再符号化が **10.17 ns/値**。比は約2.6倍。BCTを恒久的な内部表現とすると変換2回が不要になり、加算は **2.88 ns/値**。GASで書いた本方式は **6.00 ns/値**で、補正関数2回の呼び出しが残る。`-O2`でも本方式の中央値は約3.81 ns/値、変換方式は約16.54 ns/値だった。CPU周波数とWSLの揺れが大きいので、絶対時間より同一実行中の比を見る。

TITに近い10万回の更新・照会では、旧方式177 ns/操作、本方式129 ns/操作、恒久BCT表現130 ns/操作、通常の64 bit整数115 ns/操作（各5回の中央値）。恒久BCT表現は加算と大小比較、符号反転、ゼロ数の計数が簡単になる一方、ゼロ値が全trit `01` なのでゼロ初期化メモリをそのまま使えず、`min/max` の式も増える。TITでは両packed方式の差は測定の揺れの範囲内で、全体の符号化変更はまだ決めない。

この方法は二進CPUの**加算器を桁間carryに直接使う**ため、32桁のループや大きな表は不要。比較・桁演算は元の `-=01,0=00,+=10` で引き続き高速にできる。一般の掛け算・割り算には同様の単発補正はまだ見つかっていない。変換方式を基本とし、[乗数・除数の形に応じた専用経路](mul-div-sub.md)を設ける。

1回の二進加算 `a+b` のcarryだけで平衡加算を完成させる案も試したが、負方向への桁上がりが二進carryでは表せず、乱数照合で反例が出た。上記の2段階補正ではいったん通常3進数字として加え、最後にバイアスを引くことでこの問題を処理している。

「全CPUで最適」という証明ではない。命令列のスループット、依存レイテンシ、異なる符号割当、AtCoderのCPUで再比較する余地がある。
